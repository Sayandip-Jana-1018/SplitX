1. Abstract

SplitX is a production-deployed, mobile-first expense splitting web application built with Next.js 16, React 19, Prisma ORM, and PostgreSQL. The platform enables real-time group expense tracking, AI-powered receipt scanning, optimized debt settlement algorithms, and voice-based transaction input. Currently live at splitsj.vercel.app, it serves real users with features including a dual-algorithm settlement engine (Greedy Netting + Exact-Match Pruning), 18 glassmorphic color themes, PWA offline support, and comprehensive audit logging.

This synopsis documents the integration of 13 industry-standard DevOps, cloud, and infrastructure tools into the SplitX ecosystem. The implementation follows a dual-deployment architecture — the existing Vercel production deployment remains untouched while a parallel enterprise-grade infrastructure is built using AWS EKS, Terraform, Jenkins, and a full observability stack.

Key Metrics: 50+ new configuration files created across 7 implementation phases. Only 4 existing source files were modified, ensuring zero production risk.

2. Introduction & Problem Statement

2.1 Background

Modern software development demands more than just writing application code. Production-grade applications require automated testing, continuous integration, containerized deployments, infrastructure automation, monitoring, and security scanning. SplitX, while feature-complete as an application, initially lacked these enterprise DevOps capabilities.

2.2 Problem Statement

The objective of this project is to implement a comprehensive DevOps pipeline for the SplitX application that:

  • Automates the entire build, test, scan, and deploy lifecycle
  • Provisions cloud infrastructure reproducibly using Infrastructure as Code
  • Orchestrates containerized deployments with auto-scaling and self-healing
  • Monitors application health with real-time metrics and alerting
  • Enforces code quality standards and container security policies
  • Manages configuration across multiple environments consistently

2.3 Scope

The implementation integrates 13 tools organized into 7 phases: Version Control (Git), Containerization (Docker), CI/CD (Jenkins), Code Quality (SonarQube), Artifact Management (Nexus), Security (Trivy), Infrastructure as Code (Terraform), Cloud Platform (AWS), Orchestration (Kubernetes), Package Management (Helm), Monitoring (Prometheus), Visualization (Grafana), and Configuration Management (Ansible).

3. System Architecture

3.1 Application Architecture

SplitX follows a monolithic Next.js architecture using the App Router pattern. The application layer is divided into: a React 19 frontend with CSS Modules and Framer Motion animations, server-side API routes handling business logic, Prisma ORM for database operations against Neon PostgreSQL, and middleware for authentication, rate limiting, and metrics collection.

5. Git — Version Control & Collaboration

G

Git

Distributed Version Control System

Git is the foundation of the entire DevOps pipeline. Every code change, configuration file, and infrastructure definition is version-controlled, enabling traceability, collaboration, and rollback capabilities.

5.1 What It Is

Git is a distributed version control system that tracks changes in source code. Every developer has a complete copy of the repository history, enabling offline work and parallel development through branching.

5.2 How It Is Used in SplitX

Conventional Commits

All commits follow the Conventional Commits specification, enforced by commitlint. Valid types: feat:, fix:, docs:, ci:, refactor:, chore:, test:.

Pre-Commit Hooks (Husky)

Two Git hooks are configured via Husky:

  • pre-commit: Runs ESLint on all staged files. Commits are blocked if linting fails.
  • commit-msg: Validates the commit message format against conventional commit rules.

Key Configuration Files

7. Jenkins — CI/CD Pipeline Automation

J

Jenkins

Continuous Integration & Continuous Deployment

Jenkins is the central automation engine that orchestrates the entire build-to-deploy pipeline. Every code push triggers an 8-stage pipeline that tests, scans, builds, and deploys the application without manual intervention.

7.1 Custom Jenkins Docker Image

A custom Jenkins image (jenkins/Dockerfile.jenkins) is built on jenkins/jenkins:lts-jdk17 with Docker CLI, kubectl, Helm, Trivy, AWS CLI v2, and Node.js 20 pre-installed.

7.2 Eight-Stage Declarative Pipeline

StageActionFailure Behavior
1. CheckoutClone repository from GitHubPipeline aborts
2. Installnpm ci — deterministic dependency installPipeline aborts
3a. Test (parallel)npm test — run test suitePipeline aborts
3b. Lint (parallel)npm run lint — ESLint analysisPipeline aborts
4. SonarQubeStatic code analysis, quality gateWarning (non-blocking)
5. Docker BuildMulti-stage build, tagged with Git SHA + latestPipeline aborts
6. Trivy ScanCVE scan for CRITICAL vulnerabilitiesWarning + HTML report
7. Nexus PushPush image to Nexus Docker registryPipeline aborts
8. K8s Deployhelm upgrade --install (main branch only)Pipeline aborts
Key Design: Stages 3a and 3b run in parallel using Jenkins' parallel directive, reducing pipeline execution time by ~40%.

8. SonarQube — Code Quality Analysis

S

SonarQube

Static Code Analysis & Quality Gate

SonarQube performs continuous inspection of code quality, detecting bugs, code smells, security vulnerabilities, and measuring test coverage. It acts as a quality gate in the Jenkins pipeline.

8.1 Metrics Tracked

Bugs, Code Smells, Security Vulnerabilities, Security Hotspots, Duplications, and Coverage. Configuration is in sonar-project.properties which specifies source paths and exclusions for generated files.

9. Nexus — Artifact Repository

N

Sonatype Nexus 3

Universal Artifact Repository Manager

Nexus serves as a private Docker registry (port 8081 UI, port 8082 registry), storing built container images with versioned tags. Every deployed version is traceable back to its Git commit SHA.

10. Trivy — Container Security Scanning

T

Aqua Trivy

Vulnerability Scanner for Containers

Trivy scans Docker images for known CVEs in OS packages and application dependencies. Integrated into Jenkins pipeline as Stage 6, producing both console output and an archived HTML report. A standalone script (scripts/scan-image.sh) allows local scans.

19.1 Optimization Strategy

  • On-demand provisioning: terraform apply before demos, terraform destroy after
  • Local-first: Jenkins, SonarQube, Nexus, Prometheus, Grafana run locally in Docker — zero cloud cost
  • minikube for K8s testing: Full Kubernetes environment locally — EKS only for final demo
  • ECR lifecycle policy: Auto-delete images beyond last 10
Budget Impact: With a 48-hour demo window, total AWS cost is ~$9.51 per session, allowing ~10 full demos within the $100 free tier credits.
